    02 · What it is

    A machine-wide session index, with the viewer built in

    It scans every agent's transcript store on this machine — Claude Code, Codex, Qoder, QoderWork — and serves one page: a rail of sessions beside a live view of the one you picked.

    Two binaries, agent-monitor and agent-monitor-v2, share one library half and each serves both shells; they can run side by side on different ports and cache roots.

    • Read-only and loopback. It reads transcripts as the agents write them and listens on 127.0.0.1 only; the default run opens the app shell at port 2727.
    • Lazy by design. A session's durable entry under the monitor's own cache root is written by visiting it, never by a sweep — the index stays cheap on a machine with thousands of sessions.
    • Two shells, both supported. The app shell (one document over the structured index and record stream) is the default; the classic rail-and-iframe page stays until the app shell is validated in real use. A switch in each remembers the choice at <state>/ui.json; ?ui=classic or ?ui=app overrides one request without disturbing it.
    • Single-machine on purpose. One filesystem, one process table. agent-monitor-fleet is the multi-machine story: one SSH tunnel per machine and a switcher whose tabs are those monitors' own pages, unmodified, in iframes — each monitor's port read from its own lock file, never guessed.
    03 · The page

    What a reader sees, and what the words mean

    The rail clusters a root session with its sub-agents and labels each with the same small vocabulary the app shell, the classic page and the fleet page all share. The view is the live transcript: turns, tools, thinking, and what arrived while you were reading.

    04 · Acting on a session

    Answer the session that is waiting on you

    A prompt typed into the page is injected into the agent's own terminal pane. That is a write into a running process, so the monitor treats it as a security surface with exactly one implementation.

    • Pairing. The write routes need a pairing token; the cmauth cookie it sets is host-scoped, not port-scoped, so both monitors on a machine share one state directory for the token, the passcode and the grants.
    • Consent. A grant per pane plus a passcode gate; the decision “may this prompt be injected into that pane” — the session-to-pane attribution and the two send transports — lives once, in the library half, and both front-ends call it.
    • Loopback only. The page never leaves the machine; a fleet page reaches a remote monitor only through the SSH tunnel you opened.

    05 · How it is built

    One data path, and the monitor is its last stage

    Everything in the agent-replay workspace is a stage on one pipeline. Agent-specific code exists only in the decode stage; every stage above it is agent-neutral and presentation-neutral, and the crate boundaries make that the only way the arrows can point.

    A sub-agent block names a child transcript, which runs the same pipeline recursively — that return edge into discover is what makes the family clusters in the rail.

    06 · Live

    Live without a single tailer thread

    No thread waits for a transcript to grow. The fold advances on the request thread of whichever page asked — an idle page is an idle server, and a closed page costs nothing until the 30-second reap.

    • O(open turn) RAM per followed session. Finished turns cross a durability frontier and are stored put-once; only the open turn is re-derived as events arrive.
    • Committed content is sent once, ever. The html crate's RecordStore renders each committed block to its wire record as it commits, into an append-only log; the page range-reads that log itself — one serialization on disk, zero in RAM, any number of readers.
    • The next run resumes. A durable entry keeps the committed blocks and a meta stream, so a later process folds from where the last one stopped rather than from byte 0 — measured on a 107 MB transcript, 99.99 % of it is never re-read.

    Residency, per session

    registered~0

    agent + path — the default for a discovered-but-unopened session

    live residentO(open turn)

    a SharedSession: the open turn + tables; reaped after 30 s idle

    durablebytes on disk

    the committed and meta streams on disk under the monitor's root; swept after two weeks idle

    07 · The wire

    A four-number cursor, and a server that keeps no client state

    Each request carries the reader's whole position. Committed content is a pure append; only the open turn ever re-sends, and a rewrite of it bumps a generation instead of re-sending the world.

    Cursor { epoch, committed_id, provisional_gen, provisional_index }
    // the whole position, in every request
    committed zone

    how far into the append-only log this reader has read; served as a byte-range pointer into the record log

    provisional zone

    the open turn's generation and the reader's index within it; a back-patch or a finalization bumps the generation and the page replaces the small zone

    • One rule per zone: truncate to from, then extend. Both halves ship in Rust — pull on the server, PullClient as the executable specification — and the embedded page mirrors it transition for transition in the shared record-stream.js reducer.
    • Epoch is session validity: a truncation or rewrite bumps it and a stale cursor resyncs from zero, served from the retained copy — never by re-parsing.
    • N tabs, laggy tabs and fresh joiners all read one shared log at their own pace.
    08 · The data layer

    One session cache, three decisions a frontend makes

    SessionCache<P, A, E> is the layer any presentation builds on: which sessions exist, which are resident, in what representation, with what derived state, and how each one's durable entry is guarded. The monitor's three answers:

    The TUI instantiates the same type with ArcLog, a view sidecar and per-session entries; --no-cache selects Transient — still a real cache, nothing durable. Same type, both frontends.

    P · the live storeRecordStore

    committed blocks ARE the wire records — the store and the session are one object and cannot desync

    A · the sidecarServeAux

    per-session presentation state the put-once store cannot hold: titles, parents, baselines

    E · the entriesSingleWriter

    the monitor claims its whole cache root once at startup, so per-entry locks are uncontendable and simply do not exist; a second monitor is redirected to the first before any cache exists

    09 · Safety on loopback

    A link can do only what the page offered

    A served page links to files a transcript touched. Each offered path is signed with an HMAC (the key at <state>/file-sig-key, mode 0600), one stamp per capability — so a route acts only on what was offered, and a reveal link cannot be edited into a byte read.

    /file
    file stamp

    renders the bytes into the page — minted only for a path the render policy allows; not stamping is the restriction

    /__reveal
    reveal stamp

    opens the path in the file manager — hands over no bytes, so it is always minted and is the only thing a click can do where nothing renders inline

    • Which paths may render is a setting, <state>/render-policy.json: never, offered (the default when the file is absent) or allowlist with directories. It folds into the render flavor, so changing it re-renders rather than serving pages stamped under the old policy.
    • Discovery is scoped inside $HOME. A cwd outside it probes nothing, and the probe never reaches $HOME's own slug, so a store polluted by a misbehaving agent cannot leak into another directory's list.
    10 · Reusable · the Rust half

    The library half: one implementation, two front-ends

    claude-monitor is a library and a binary. agent-monitor-v2 composes a different session page over the same modules — “a front-end, not a second implementation” — and everything a third front-end would need is already public.

    12 · Reusable · the layers below

    Three ways in, smallest first

    The monitor is the largest consumer of the workspace library; the same layers are open to any program. Pick the dependency by the job.

    + presentcore + syntect

    build a frontend: the session cache, the pull protocol with both halves, fold policy, summaries and highlighting — a native app, a bot, a notebook widget

    + tui / htmlthe finished viewers

    embed the terminal viewer or the HTML exporter and live server from your own binary

    # discovery, across every agent's store, windowed before any transcript is opened agent-replay --paths --all --since 24h # content: one JSON object per block, from the same fold every frontend renders agent-replay <path> --dump - --json
    • Adding an agent touches no shared code. Implement TranscriptAdapter over the audited seam, mint an id with Agent::new("gemini") — an open interned id, not an enum — and register it; the monitor lists the new store through discovery with no change of its own.
    13 · Kept honest

    Every change is gated, and the browser is one of the gates

    The workspace is fully testable without a terminal, and the monitor's behaviour — positioning, search through growth, the tail pin, the virtual DOM — is pinned by real-engine cases against both shells.

    A queued bug's reproduction is checked in under a known_red_<task> name and skipped by the gate; the fix removes the marker. The classic page is the behavioural reference the app shell is measured against.
